# tech-calendar 再開日記 — 現状整理から README、そしてモバイルへ

2026年7月24日夜。しばらく触っていなかった `tech-calendar` リポジトリを開き直し、まずは「いま何があるのか」を確認するところから始めた。

## プロトタイプの姿が見えてきた

リポジトリは 2026年1月に作られた Vite + React + TypeScript のイベントカレンダーだ。日本の祝日とイベントを JSONL から読み込み、月表示のカレンダーで日付を選ぶと一覧が出る。見た目は一通り動くが、README はタイトル一行だけ、`package.json` の名前もスターターのままで、いわゆる「Bolt で作って置いてある」段階だった。

Supabase の SDK は依存に入っているもののコードでは未使用。サンプルデータは 2026年想定のイベント6件・祝日16件。コミット履歴も初期化と Vite の base path 調整が中心で、長く放置されていたことが分かる。

「まず現状を README に書いて」という依頼で、機能・スタック・セットアップ・データ形式・ディレクトリ構成をまとめた。プロトタイプであること、静的 JSONL で動いていること、バックエンド未実装であることも明示した。これで次に触る人が、リポジトリを開いた瞬間に地図を手にできる。

## 「公開URL」の誤解と GitHub Pages の落とし穴

GitHub 上のリポジトリ URL を「公開URL」と伝えたところ、404 になったという報告があった。実際にはリポジトリページ自体は開く。一方で GitHub Pages は有効で、`https://windhole.github.io/tech-calendar/` も応答する。ただし公開しているのはビルド成果物ではなくソース一式だ。ブラウザは `.tsx` をそのまま実行できないため、アセット取得で実質的に壊れている。

つまり「ソースの置き場」と「動くアプリの URL」が混同されていた。Pages を正しく動かすには、`npm run build` の結果をデプロイする仕組みがまだ必要だ。

## エージェント作業を iPhone から続けるには

夜の続きとして、このエージェント作業を iOS からも操作する方法を調べた。Cursor for iOS は導入済みだった。やり方は大きく二つある。

- **Cloud Agents** — スマホからリポジトリを選んで新規タスクを投げる（PC 不要）
- **Remote Control** — デスクトップで動かしているこのセッションを、スマホから追操作する

Remote Control はエージェント側から自動で有効化できず、チャット入力で `/remote-control` を実行する必要がある、というところまで確認した。

## いま書いていること

セッションの締めとして、今日ここまでの作業をブログ風に残すことにした。保存先は `blog/`、ファイル名は日付と時刻。そして同じ運用を、このリポジトリのプロジェクトルールとしても登録する。

まだアプリ本体の機能追加や Pages の正式デプロイには手を付けていない。それでも「何があるか分からないリポジトリ」から、「地図があり、作業ログが残り、モバイルでも続けられる土台」までは進んだ一日だった。
